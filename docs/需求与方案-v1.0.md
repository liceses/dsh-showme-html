**一句话定稿：**

> `showmeWithHTML` 给 agent 一个**汇报动作**：把它写好的汇报页（工作区里的 HTML 文件）直接推到对话里渲染出来，让"成果汇报"从 Markdown 长文变成一页可读、可放大、可留档的静态网页。

## 1. 为什么这不是重复建设（必须先说清）

DSH **已经**能在右侧栏预览 HTML 文件（`dsh-client-ui-sidebar-documentpreview`，含脚本沙箱、相对资源加载）。所以本插件的价值**不在渲染**，而在这三条：

| 现有能力 | 本插件补上的 | 为什么重要 |
|---|---|---|
| 用户**点开文件树**才能看 | agent **主动把它推到对话里** | 汇报是"我说完了，你看"，不该让用户去找 |
| 内容是"文件地址"，展示靠导航 | 展示是**一次对话动作**，与回合、结论、证据绑在一起 | 汇报页和它对应的结论在同一个视野里 |
| 通用预览器（任何文件都一个样） | **汇报专用卡**：标题、结论、路径、全屏、留档 | 汇报页需要的是"读完就懂"，不是"文件查看器" |

**结论：本插件是"展示动作 + 汇报形态"，不是"又一个 HTML 预览器"。** 这条边界决定了后面所有取舍。

## 2. 需求定稿

### 2.1 用户故事

- **US-1**：当 agent 完成一段有结构的工作（调研、改造、对比、分析），我希望它用一页 HTML 汇报，而不是 200 行 Markdown。
- **US-2**：这个汇报页要**直接出现在对话里**，我不用去文件树里找、不用切浏览器。
- **US-3**：汇报页要能**放大看**（全屏），因为里面有图表/表格/长内容。
- **US-4**：我要知道这页对应哪个文件；看完能留着，也能自己打开编辑器改。
- **US-5**：如果这页没写好、文件丢了、被沙箱拦了，我要看到**人话解释**，而不是白屏。
- **US-6**（明确延后）：我想在页面上点选、打勾、提交，让 agent 拿到我的反馈。

### 2.2 功能需求

| ID | 需求 | 优先级 |
|---|---|---|
| FR-1 | 宿主注册模型工具 `show_html`，参数：`path`（必需，工作区相对路径）、`title`（可选，卡片标题）、`note`（可选，一句话说明为什么值得看） | P0 |
| FR-2 | `execute` 校验：文件存在、是普通文件、扩展名 `.html/.htm`、大小在限额内；失败给出可操作的错误文本 | P0 |
| FR-3 | 工具**输出**只回传结构化的轻量元数据（路径、标题、字节数、状态），**绝不回显 HTML 正文**（避免双倍 token） | P0 |
| FR-4 | 客户端以 `show_html` 为键注册对话内卡片（`tool.call.toolview`） | P0 |
| FR-5 | 卡片渲染：贴边 iframe + 沙箱（不低于现有预览基线）、固定可视高度、内部独立滚动 | P0 |
| FR-6 | 卡片头部：标题、源文件路径（可点击在右侧栏打开）、**刷新**、**全屏** | P0 |
| FR-7 | 全屏：走框架级悬浮层（`shell.overlay`），非破坏性、可 Esc 退出、退出后回到对话原位 | P1 |
| FR-8 | 错误态：文件不存在 / 非 HTML / 超限 / 沙箱拦截，各自给出可操作提示 + 重试 | P0 |
| FR-9 | 非可见卡片不持有活 iframe（对话变长后必须卸载），可见时恢复 | P0 |
| FR-10 | 设置项：汇报页推荐目录、卡片默认高度、是否在写入后自动展示 | P2 |
| FR-11 | 页面 → 卡片的交互回传（`postMessage` 白名单 + 结构化校验），再由卡片交给模型 | P3（你已划为扩展） |
| FR-12 | 文件变更后自动刷新（watch + 通知通道） | P3（你已划为扩展） |

### 2.3 非功能需求

- **NFR-1 安全**：iframe 永不获得应用同源权限；不注入凭据；页面内的脚本可执行（这正是 HTML 汇报的价值），因此必须显式接受"agent 生成的脚本会在你的浏览器里跑"这一事实，并把它写进 README。
- **NFR-2 成本**：本插件本身**不产生任何额外推理**；HTML 的生成成本属于模型侧，靠"何时该用"的边界与模板骨架控制。
- **NFR-3 性能**：20 条历史卡片不得让会话卡顿（靠 FR-9）。
- **NFR-4 不污染**：不写用户仓库（除汇报页本身的目标目录）、不改用户配置、不留残留监听与路由。
- **NFR-5 可卸**：停用插件后无残留槽位、无残留 iframe、无控制台报错。

### 2.4 验收标准（可测）

1. agent 完成一段工作后调用 `show_html`，**无需任何手动点击**，对话内出现渲染好的汇报页。
2. 工具调用参数与返回值里**都不含 HTML 正文**（只有路径与元数据）。
3. 点"全屏"后页面占满窗口，Esc 退出后回到对话原位、滚动位置不失。
4. 指向一个 200 KB 的本地 HTML，2 秒内出首屏。
5. 文件不存在 / 是 `.md` / 超过限额，三种情况各给出不同且可操作的中文提示。
6. 会话里连续展示 20 次后滚动仍流畅。
7. 停用插件后重载 GUI，无残留、无报错。

### 2.5 明确不做（Non-goals）

- ❌ 不做通用浏览器（地址栏/标签页/书签/书签栏）。
- ❌ **MVP 不做内联 HTML 字符串**（你已选文件优先；这也是 token 与留档的正确答案）。
- ❌ MVP 不做自动刷新、不做宿主↔页面回传、不做服务化。
- ❌ 不做远程 URL 渲染。
- ❌ 不做"每回合强制生成汇报"的自动触发（见 §5 决策点 1）。
- ❌ 不复刻文件树里的通用预览（DSH 自带）。

## 3. 技术方案

### 3.1 形态（已核实的骨架）

```
showmeWithHTML/
├─ package.json          # name/version/exports + dsh.bundle.patch + dsh.client{platform:web, inject:[...]}
├─ cordis.patch.yml      # - insert: [{ id: showme-html, name: '<pkg>' }]
├─ tsdown.config.ts      # 双配置：node 半区 lib/index.js + 浏览器半区 lib/client.js（closure-factory banner）
├─ tsconfig.json / tsconfig.build.json
├─ src/
│  ├─ index.ts           # 宿主半区：注册 show_html 工具
│  ├─ protocol.ts        # 宿主/浏览器共享常量（工具名、限额、槽位 id）
│  └─ client/
│     ├─ index.ts        # 浏览器半区：注册槽位
│     ├─ ReportCard.tsx  # 对话内汇报卡
│     ├─ Fullscreen.tsx  # shell.overlay 全屏宿主
│     └─ read.ts         # 复用 workspaceFiles remote 读取字节 → Blob URL
└─ README.md
```

装配：`dsh plugin --profile web add link:D:\developing\DSH-plugin\showmeWithHTML`。
**注意**：client 半区改动只在 `pnpm run dev:web` 同时运行时免刷新；否则需重启/刷新。这条要写进 README。

### 3.2 展示位决策（我替你定的，可推翻）

| 候选 | 判断 |
|---|---|
| **对话内卡片** ✅ 选它 | "汇报"的语义就是"就在结论旁边"。实现量最小，历史天然可回看，不引入任何导航状态。 |
| 右侧栏 tab | 与 DSH 自带文件预览同一区域，价值被稀释；用户还得手动开。 |
| 中央全局面板 | 要自建"当前展示什么"的状态机与入口图标，MVP 阶段是纯粹的复杂度。 |
| 悬浮层 | 适合"临时瞄一眼"，但接管整个汇报会遮住对话、生命周期更难管。**把它降级为卡片上的"全屏"按钮。** |

### 3.3 宿主半区（代码级契约，均已在本机版本核实）

```ts
// src/index.ts
import { defineTool } from '@deepseek-ai/dsh-tools'   // 与 dsh-tool-present 同款
export const name = 'showme-html'
export const inject = ['tools', 'fs']
export function apply(ctx, config) {
  ctx.tools.register(defineTool({
    name: 'show_html',
    description: /* 强引导：汇报/讲解用；优先相对路径；不要用它贴代码 */,
    parameters: { path: {...}, title: {...}, note: {...} },
    output: { schema: {...}, render: (args, v) => [{ type: 'text', text: `已展示 ${v.path}` }] },
    async execute(args, exec) {
      // ctx.fs.resolve / ctx.fs.stat 校验；return { path, title, bytes, ok: true }
    },
  }))
}
```

**不需要自建 HTTP 路由**：内容由浏览器半区经现成的 `remote.workspaceFiles.readAll(sessionId, path, signal)` 取字节（现有文档预览就是这条路），再转 Blob URL 塞进 iframe。比 `dsh-text-drop` 更省事。

### 3.4 浏览器半区

```ts
// src/client/index.ts
ctx.slots.inject('tool.call.toolview', () => ctx.slots.register(
  { name: 'tool.call.toolview', key: 'show_html' }, ReportCard))   // 对话内卡片
ctx.slots.inject('shell.overlay', () => ctx.slots.register(
  { name: 'shell.overlay', id: 'showme-fullscreen' }, Fullscreen)) // 全屏层
```

- 沙箱基线对齐现有预览：`sandbox="allow-scripts"`，**不含** `allow-same-origin`。
- `package.json` 的 `dsh.client.inject` 需声明：`@deepseek-ai/dsh-client-runtime`、`@deepseek-ai/dsh-client-ui-slots`、`@deepseek-ai/dsh-api-workspace-files` 等（实现时逐个以实际版本为准）。

### 3.5 汇报页放哪（待你定，见 §5 决策点 2）

推荐 **`.dsh/showme/`**：与 DSH 自己的 `.dsh/drops/` 同族、不出现在你的源码树里、不进 git。次选工作区根 `showme/`（可见、可提交、可分享）。

### 3.6 ⚠️ 这个项目的成败点不在渲染管道

**渲染管道最多 2 天就能做完，而且做完之后你会发现"能不能用"完全取决于汇报页写得好不好。**

如果 agent 每次手搓的 HTML 又丑、风格又不统一、信息层级又乱，你会立刻退回 Markdown——那时插件技术上成功、产品上失败。

所以真正的工作量在这两件事上：

1. **一套自包含汇报模板**（单文件、内联 CSS、零外部依赖、离线可用）：结论区 / 证据区 / 表格 / 时间线 / 代码块 / 对比栏，加明暗两套配色。
2. **一份写作规范**，教模型：什么时候该用 HTML 汇报、什么时候别用、一页里该放什么、放多少、怎么排。

我的建议是**把模板与规范做成一个 DSH skill**（走现有 skill 机制），插件只管展示管道。这样：模板可迭代而不用重装插件、模型按需读取而不占常驻上下文、与你的 skill 生态一致。

## 5. 利弊与局限（认账清单）

### 这个方向天然的优势

- **零额外推理成本**：插件不调用模型，不烧 token；贵的是"生成 HTML"这件事本身，而那由使用边界控制。
- **落地快**：无路由、无推送通道、无状态机；所用的每个 API 在本机版本都已验证存在。
- **不重复造轮子**：内容读取复用现成 remote，渲染复用现成沙箱策略。

### 硬局限

| # | 局限 | 后果 | 应对 |
|---|---|---|---|
| L1 | `sandbox="allow-scripts"` 且无 `allow-same-origin` | 页面处于不透明源：`localStorage`/cookie 不可用、`alert` 需 `allow-modals`、表单提交需 `allow-forms`、下载需 `allow-downloads`、所有 `fetch` 皆跨域 | 模板与规范里明确"能写什么"；拦截图给可读解释 |
| L2 | iframe ≠ 真实浏览器 | 页面在别处打开可能长得不一样 | README 如实说明，别宣称"真实预览" |
| L3 | agent 生成的脚本会在用户浏览器里执行 | 理论上的数据外泄/骚扰面 | 沙箱隔离；README 显著声明；不注入任何凭据 |
| L4 | 文件被改/删后老卡片怎么办 | 显示内容不确定 | 建议"实时读 + 文件没了就显示已删除"，MVP 可先做"读不到就报错+重试" |
| L5 | 长会话多个活 iframe | 掉帧 | FR-9 非可见卸载 |
| L6 | 生成 HTML 比写 Markdown 贵 | 用多了反而不划算 | 明确适用边界（结构性/可视化/成果汇报用；闲聊短答不用） |
| L7 | 与右侧栏预览功能相邻 | 用户可能觉得"这不就是预览吗" | §1 的三条差异化必须落到 UI 上（主动推、跟对话、汇报专用卡） |
| L8 | Windows 路径 / 中文路径 / 工作区相对路径 | 解析错误 | 一律走 Session 文件系统解析，不自己拼路径 |
| L9 | client 半区改动需 `dev:web` 或重启才生效 | 开发体感差 | README 写明；开发期常驻 `pnpm run dev:web` |

### 最大的非技术风险

> **"HTML 汇报比 Markdown 方便"这句话目前是假设，不是事实。**
> 它成立的条件是：汇报页**默认就好看**、**生成成本可接受**、**只在值得的时候用**。
> 三者任一不成立，用户就会退回 Markdown，插件沦为"偶尔用一下的玩具"。
> —— 这也正是 §3.6 把 M3 定为核心里程碑的原因。
