## 0. 为什么需要这份计划

DSH 0.1.7 的 web 组合里，下面这些**原生行已挂载**：

| 原生 entry | 包 | 与本插件的关系 |
|---|---|---|
| `ui-sidebar-documentpreview` | `@deepseek-ai/dsh-client-ui-sidebar-documentpreview` | 右侧栏原生预览 html / code / image / pdf / office / excel / markdown / text |
| `dsh-client-ui-deliverables` | 同名 | 交付物卡片（presentation 表面） |
| `dsh-tool-present` / `dsh-agent-tool-presentation` | 同名 | 交付物呈现链路（注意：后者是 **native/ptc 工具呈现模式**，与交付物卡片无关） |

本插件的价值**从来不是渲染**（`docs/需求与方案-v1.0.md` 第 30 行就写明：
「DSH 已经能在右侧栏预览 HTML 文件……所以本插件的价值不在渲染，而在这三条」）。
它的独有价值是**反馈闭环**：页面上的「点名 + 表态」→ 一行回执 → 填入输入框 → 回到 agent。

所以目标不是"取代原生预览"，而是：**让原生预览成为这条链路的一部分，且互不抢占地盘。**

## 2. 0.1.7 已核实的扩展点（**已用真实实现逐条核对**）

> ⚠️ 原版这一节写的是"`sidebarRightTabs` 这个名字在 `.d.ts` 里搜不到，不要照抄"。
> **那个结论是错的** —— 打包后的应用里根本没有 `.d.ts`，搜不到不等于不存在。
> 从 `app.asar` 里的 README 与实现核对后，正确结论如下。

### 2.1 `ctx.sidebarRightTabs` —— **存在**，是"tab 类型"注册表

```ts
ctx.sidebarRightTabs.register({
  id,                     // 本实现的身份，全局唯一（同一 id 第二次注册 throw）
  kind,                   // tab 类型名；一个 kind 最多一份 builtin + 一份 extension
  patterns?,              // 作用于 dsh-resource:// 地址的 glob：含 ':' 的匹配整个地址
  priority?,              // 'builtin' | 'extension' | 'fallback'
  canOpen?,               // 否决一次命中
  title,                  // tab chip 的文字
  guide?,
  keepMounted?,
})
```

- 原生 documentpreview 用的是 `kind: 'text'` + `pattern: 'dsh-resource://file/**'` + `priority: 'fallback'`。
- `priority` 是**三值**枚举（原计划写的"二值 builtin/extension"漏了 `fallback`）。

### 2.2 `ctx.sidebarRight.openResource / openTab` —— 失败是 **throw**，不是静默 return

原计划 §P1 写着「0.1.7 的一个已知坑：`service.openTab` 对未注册类型会静默 return」。
实测相反：`dsh-resource://` 之外的地址、无人认领的地址、未注册的 kind **都会 throw**
（README 原文："那是接线错误，不是用户错误"）。而且原生 `openFile` 是 `async` 的，
失败以 **rejected promise** 回来 —— 同步 `try/catch` 抓不到它。
P1 的兜底因此必须挂在 promise 上（见 §3 P1）。

### 2.3 文件地址语法属于框架，插件不要自己拼

```js
// @deepseek-ai/dsh-util-workspace-path
sessionFileAddress(sessionId, path) → 'dsh-resource://file/session/<sessionId>/<path>'
fileAddressFor(sessionId, cwd, path) → 相对路径 / 工作区内绝对路径都收敛成上面那个形式
```

容器给槽位组件的标准属性 `openFile(path, options?)` 内部就是
`ctx.sidebarRight.openResource(fileAddressFor(sessionId, cwd, path))`。
**用这个属性就够了**，插件自己拼地址只会拼错
（`test/client-bundle.test.mjs` 有一条静态门禁盯着"源码里不许出现 dsh-resource://"）。

### 2.4 `ctx.documentPreviews` —— 只有 `register()`，**没有读取面**

```ts
ctx.documentPreviews.register({ id, extensions, binaryExtensions?, priority, title, loading, wrap? })
```

注册表是闭包里的一个 `Map`，对外只有 `register()`。**所以原计划 P0 想要的
"启动时读注册表快照、发现误认领就警告"写不出来** —— 没有可读的 API。
P0 因此改成静态门禁（见 §3 P0）。

### 2.5 原生文档预览怎么渲染 HTML（**决定 P1 走向的一段**）

来自 `@deepseek-ai/dsh-client-ui-sidebar-documentpreview/lib/client.js`：

1. `packHtml` 收集页面里**相对的**、**直接**的 `script[src]`（经典 JS）与
   `link[href]`（stylesheet）——**只有这两类**。图片、下级页、ES module、
   CSS `url()` / `@import`、动态构造的 URL **都不在收集范围**（注释里明说 unsupported）。
2. 它把这份 HTML 与资产交给一个**固定 bootstrap**：bootstrap 在 iframe **内部**
   为每个资产建 blob URL 再改写属性，然后 `document.write()` 进 iframe。
3. iframe 的地址是 `URL.createObjectURL(new Blob([html]))` —— 即 **blob:<uuid>**，
   所以文档里的 `location` 只有一串 uuid；相对引用（没被改写的那些）也按这个 blob 基址解析。
4. 例外：页面若自己带 `<base href>`，`packHtml` 直接跳过打包（"URL 解析交给浏览器"）。

结论：**原生文档预览是"自包含单文件 HTML"的预览器**，不是"按目录解析的工作区页面"预览器。
本插件的页面恰恰依赖目录解析（预设 CSS、`templates/core.js`、同目录数据文件、页面旁的图片），
所以它只能当**旁路**（卡片右下角的路径按钮），不能当主链路。

### 2.6 右栏 Browser tab 的地址政策

`ui-sidebar-browser` 的 README：地址解析器接受 HTTP / HTTPS（含 loopback），但**拒绝**
`file:`、`data:` / `blob:`、内嵌凭据、**DSH 应用自身 origin**、畸形地址；本地文件由
Document Preview 负责。我们两条都不通 —— 所以只能注册自己的页类型（见 §3 P1）。

### P0 —— 零风险的共存加固 ✅ 已完成

1. **明确不认领全局 `html` 后缀**：不加 `documentPreviews.register`，保持原生 `builtin`
   预览是 `.html` 的默认归宿。插件从未注册过，这条是"守住"，不是"改代码"。
2. **运行时自检 → 改为静态门禁**（原因见 §2.4）。`test/client-bundle.test.mjs`
   新增三条断言：源码里不许出现 `documentPreviews.register` /
   `ctx.get('documentPreviews')` / `sidebarRightTabs.register`；不许出现
   `dsh-resource://` 字面量；`inject` 只能是 `['slots']`（不硬依赖原生预览包，
   缺了它也不会停在 pending）。
3. 门禁扫描**先剥掉注释**：注释里会写"不注册 documentPreviews"这类反例句子，
   拿原文件断言只会咬到自己（第一版就踩了）。

### P1 —— 卡片头部新增「侧栏打开」 ✅ 已完成（**两易其稿**）

**第一稿（已废弃）**：用座位标准属性 `openFile(path)` 把文件交给原生文档预览。
**现场把它否了**（2026-09-26，用户点「原生预览」后报"没找到数据文件：<一串 uuid>.data.js"）：

| 候选表面 | 为什么不行 |
|---|---|
| 原生**文档预览**（`openFile`） | 它把 HTML 塞进 **blob iframe**（`URL.createObjectURL(new Blob([html]))`），只把相对的 `.js` / `.css` 打包成 blob（`packHtml`）。于是**相对图片、下级页、CSS `url()`**、以及"按自己文件名推导数据文件"**全部失效** —— 报出来的文件名就是那个 blob uuid。本插件的地基（页面内相对引用天然可用）在这里被抽掉了。 |
| 右栏 **Browser tab**（`openTab('browser')`） | 它的地址校验明确**拒绝 DSH 应用自身 origin**（README 原文），而镜像路由正在那个 origin 上。 |

**第二稿（已实施）**：**自己注册一个右栏页类型**，正文渲染我们自己的镜像地址。

```js
// 页类型：按 kind 打开，不给 patterns / canOpen —— 不认领任何后缀，不抢地盘
ctx.inject(['sidebarRightTabs', 'sidebarRight'], (scope) => {
  scope.effect(() => scope.sidebarRightTabs.register({
    id: 'dsh-showme-html', kind: 'showme-page', multiple: true,
    priority: 'builtin', title: () => '展示页',
  }), 'dsh-showme-html: sidebar page type')
  scope.effect(() => scope.slots.inject('sidebar.right.pane.tab', () =>
    scope.slots.register({ name: 'sidebar.right.pane.tab', key: 'dsh-showme-html' }, SidebarTabBody),
  ), 'dsh-showme-html: sidebar page body')
})

// 打开：卡片头部「侧栏打开」
ctx.sidebarRight.openTab('showme-page', { params: { url: <镜像地址>, title } })
```

- 正文从 `useTabInfo().tab.navigation.params` 取 `{ url, title }`（与 `ui-sidebar-browser`
  取 `params.url` 是同一套），渲染 iframe + 底部回执栏（回执可一键填入输入框）。
- 右栏服务不在时：`ctx.inject` 那段不跑，卡片照旧可用；点按钮则兜底到新标签页。
  插件本体的 `exports.inject` 仍然只有 `['slots']` —— 附加能力不拖核心功能。
- 反馈闭环不受影响：卡片主体、底部反馈条、输入框回填都在原处。

**验收**：点「侧栏打开」后页面出现在右侧栏 tab 里（正文走镜像路由，相对引用照旧），
且回执栏可用。离线 52 项客户端断言覆盖注册形状、参数、兜底与正文渲染。

### P2 —— 与原生交付物对齐 ⚠️ 原前提不成立，需重新定义

原计划假设"同一条 `show_html` 结果会被原生 deliverables 重复渲染成第二张卡片"。
核实后**不成立** —— 这次是逐行读实现确认的，不是读 README 推断的：

- `@deepseek-ai/dsh-client-ui-deliverables/lib/client.js` 里，产出路径的唯一来源是一张
  按工具名的 switch，只认 `write` / `edit` / `str_replace_editor`（后者还要是"有修改作用"
  的命令），外加 `deliverables/presented` 事件折叠出来的交付文件。
  在这个包里搜不到 `show_html` —— 没有任何分支会碰它，所以**不可能**出现第二张卡片。
- `output.presentationMeta` 的形状（`{ bytes, url }`）与 `defineTool` 的契约一致
  （`output` 必须是 `{ schema, render, presentationMeta? }`，其中 `presentationMeta`
  必须是函数），而这份 meta **只被本插件自己的卡片读**（`block.meta`）——
  它没有跨包消费方。

**真正还值得做的**（属于新功能，不是"对齐"）：让 `show_html` 的产物进入原生交付物链路
（`present` 那条），从而蹭到原生卡片的操作面（在关联应用打开、变更对比）。
那要先决定"一页 HTML 算不算交付物"、是否值得多调一次 `present`。**默认不做。**

### P3 —— 让原生预览也能吃到反馈闭环（可选，默认不做）

路径仍然成立：
`documentPreviews.register({ extensions: ['html','htm'], priority: 'extension', ... })`
注册一个本插件专用渲染器，里面复用现有的反馈注入脚本。
**必须**同时确认普通 `.html` 仍走原生 `builtin`（靠 P0 的门禁守）。
收益/风险比最低，**默认不做**。

## 4. 不做什么（明确的负面清单）

- ❌ 不认领 `png/jpg/pdf/xlsx/docx/…` —— 原生 `ui-sidebar-documentpreview` 已全覆盖。
- ❌ 不自己拼 `dsh-resource://` 地址（有静态门禁盯着）。
- ❌ 不把展示页**当主链路**交给原生文档预览（理由见 §2.5：blob iframe 会毁掉相对引用
  与数据文件命名）。它仍然可以从卡片右下角的路径按钮进 —— 那是旁路。
- ❌ 不为了"兼容原生"把自绘全屏（`shell.overlay`）删掉 —— 原生预览在**右栏**，
  全屏是**画面内**，两者是不同场景，保留。
  （全屏的控件全部放在**底部**：Windows 桌面端顶部 40px 是原生窗口按钮，
  画在网页之上，放在那里永远点不到 —— 2026-09-26 现场 bug，已修。）
- ❌ 不改宿主那条带围栏的路由（403/404/415 的边界已过测试，见 `test/route.test.mjs`，
  并由 `test/live-probe.mjs` 对着运行中的实例验过）。
